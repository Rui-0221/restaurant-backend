# AI 点餐链路

## 产品边界

AI 只负责聊天中的推荐，不读取、分析或干预手动点餐的购物车。顾客点击“加入购物车”后，由普通购物车合并推荐菜品；同菜品累计数量，已有手动菜品保留。可在购物车统一编辑，最后走普通下单，创建订单或加入本桌的活跃订单。

退出 AI 页面会中止浏览器请求，并通知后端取消当前生成。已完成的对话保留；迟到回复不覆盖新对话、不加入购物车。取消通知支持先于聊天请求到达，也支持请求落到不同后端实例。断网或强制关闭进程时通知可能送达失败，后端请求仍有超时上限；上游模型是否立即停止计算由提供方决定。

## 架构

```text
用户消息 + 本店已核实菜单 + AI 会话需求
                    ↓
        DeepSeekDishSelectionAdapter
       理解自然语言，返回结构化需求和选择
                    ↓
           RecommendationPolicy
       校验菜品、数量、价格及已识别条件
                    ↓
        Redis 会话保存 → 推荐预览
                              ↓ 点击加入
手动选菜 ───────────────→ 普通购物车
                              ↓ 确认下单
                    OrdersService.placeOrder
                   事务内去重、建单或同桌加菜
```

- `AiOrderingServiceImpl` 编排菜单、会话、模型与校验，不依赖订单服务。
- `DeepSeekDishSelectionAdapter` 封装提示词、JDK HttpClient、严格 JSON 解析、超时和上游取消。
- `RecommendationPolicy` 集中校验结构化推荐，不解析自然语言。
- `RedisAiOrderConversationManager` 封装会话归属、需求与历史、轮次、限流、取消。

没有独立 AI 购物车、AI 确认服务或 Redis 方案领取状态。没有增加 Spring AI、RAG、向量数据库或自主工具执行框架。普通订单服务的桌台 CAS、活跃订单唯一约束、加菜行锁、事务后通知保持原有职责。

## HTTP 协议

三个 AI 接口均使用顾客 JWT，身份不从请求体获取。

### 读取用餐标识

`GET /users/ai-order/meal/{tableId}` 返回 `Result<Long>`，只包含用餐标识，不返回订单或购物车内容。前端在恢复聊天和应用推荐前检查该标识。

桌台的空闲版本与紧随其后的占用版本映射为同一餐；释放桌台后标识前进。后端在模型调用前后也检查用餐标识。

### 聊天

`POST /users/ai-order/chat`：

```json
{
  "tableId": 1,
  "requestId": "0c35e2d9e36b481b8e458de0da32f619",
  "message": "两个人，想吃清淡不辣的菜"
}
```

首轮省略 conversationId，后续请求使用响应中的 conversationId。ID 限 1～64 位字母、数字、下划线或连字符。每轮生成新的 `requestId`，不要复用已取消请求的 ID。消息最多 500 字，不发送购物车内容。

响应采用项目统一的 `Result` 信封，`data` 为：

```json
{
  "action": "PROPOSAL",
  "reply": "已搭配好，请查看后加入购物车",
  "items": [
    { "dishId": 1, "name": "白切鸡", "amount": 1, "price": 28.00, "reason": "符合清淡口味" }
  ],
  "totalAmount": 28.00,
  "conversationId": "后端生成的会话ID",
  "errorCode": null
}
```

| action | 行为 |
| --- | --- |
| `PROPOSAL` | 展示推荐，等待顾客点击加入购物车 |
| `ASK_CLARIFICATION` | 继续聊天补充需求，不提供可应用菜品 |
| `MANUAL_ORDER` | 展示失败原因，可重试或手动点餐 |

错误保留结构化 `errorCode`，包括模型不可用、状态不可用、限流、会话缺失、归属不符、旧轮次和取消。客户端需同时处理 HTTP 状态和 `Result.code`。

旧 `POST /users/ai-order/confirm` 已移除，响应不再包含 `proposalId` 或 `source`。

### 取消

`POST /users/ai-order/cancel`：

```json
{ "requestId": "正在生成的请求ID" }
```

前端使用 AbortController 中止等待，并通过带顾客身份的 keepalive 请求通知后端。后端每次等待上游响应时检查 Redis 取消标记，取消 HTTP future；写入历史时再次原子校验取消标记与轮次。

## 需求和校验

模型负责数量、否定、改口、指代、人数、预算、菜系和忌口的理解；后台保存 `DiningPreferences`，不增加表单。不明确时追问。

已明确的过敏和食材排除项合并保留，不会因历史截断或模型漏写而删除。撤销已有硬性忌口需点击“重新开始”；普通菜系、人数、预算使用模型输出的当前完整需求。辣度在模型未输出时沿用已知值。

会话绑定顾客、桌台和本次用餐，默认 30 分钟滑动过期，最多保留最近 20 轮；需求独立保存，历史记录实际推荐菜品，便于理解“把上一道换掉”。新一餐、过期或“重新开始”会开启新会话。默认每位顾客每分钟最多 10 次聊天请求。

推荐只使用在售且 AI 资料为 `VERIFIED` 的菜品。后端拒绝未知菜品 ID、非法数量和超过 99 份的重复合并结果，并根据目录重新计价，检查已识别的预算、菜系、辣度和食材排除。过敏原为空或 `UNKNOWN` 表示未知；有食材排除条件时不推荐这些菜品。

这些检查只作用于 AI 推荐。模型识别与目录资料仍可能有遗漏，不能保证理解所有别名或模糊表达。普通购物车和普通下单不读取 AI 忌口；用户手动选择什么，由用户决定。下单重新检查在售状态与数据库价格，不锁定推荐时的预览价格。

## 普通下单去重与升级

`POST /orders/scan-order` 新增可选 `requestId`，格式同上。顾客端会自动生成并存入 sessionStorage：同一次提交遇到网络失败或刷新后重试，沿用相同 ID；成功后下一次加菜使用新 ID。

`order_submission` 以请求 ID 为主键，绑定调用身份和桌台、菜品数量的摘要。请求记录与订单在同一 MySQL 事务提交；并发重试等待后读取已有订单，不重复加菜。失败时一起回滚，可以使用同一 ID 重试。不同身份或内容不能复用同一 ID。成功重试返回关联订单的当前详情，不保存首次响应快照。未提供 ID 的旧客户端保留原行为，没有这一去重保障。

升级已有数据库先执行 [20260913_01_order_submission.sql](../src/main/resources/db/migration/20260913_01_order_submission.sql)，再同步更新后端与顾客端。本迁移只创建普通提交记录表。已有库的旧 `ai_order_submission` 表保留历史但不再被应用读取，新库不再创建该表；旧 Redis 会话等待自然过期，新链路使用 `restaurant:ai-order:v2:`。不要用 `init.sql` 升级已有数据库，它会重建业务表。

## 验证

- 推荐规则测试：候选 ID、重复数量、条件保留、菜系改口、未知过敏原、预算等。
- 会话测试：真实本地 Redis，专用随机前缀，验证取消竞态、旧轮次、历史截断、跨餐失效和过期；只清理自己的键。
- 全链路测试：本地隔离 MySQL 和 Redis，验证顾客鉴权、推荐不下单、普通提交、并发去重和失败回滚。
- 模型适配器测试：模拟异常 JSON 和响应，并使用本地 HTTP 服务验证真实网络请求及取消。
- 顾客端测试：共享购物车保留手动菜品、批量合并失败不部分写入、离页取消与迟到结果隔离、自动滚动、中文输入法和重试 ID。

真实 DeepSeek 测试需显式设置 `RUN_LIVE_AI_TESTS=true` 并提供有效 `DEEPSEEK_API_KEY`；默认跳过，不会因本地已有 Key 自动产生调用。
